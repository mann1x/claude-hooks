## Description
Owner request 2026-10-24, after the osync thread. A cloud thread linked to solidpc gets only the pgvector mailbox tools (send/list/read/ack/edit/cancel/sent/sessions), and every one acts as the linked machine's session (claude-hooks@solidpc). There is no alias op and no "from"/reply-to field. So osync's mail to xOllama went out as claude-hooks; xOllama replied there (osync read it via that inbox, #1893) but saw no osync address and assumed the reply wouldn't reach it. osync@cloud was registered once (2026-10-02, file relay on pandorum through a Remote Control session), then lapsed; re-registering needs the owner to approve a card in the cloud app each time.
Wanted: lasting registrations. An alias op (or a `from` alias on send) in the pgvector mailbox MCP, so a linked cloud thread can register / send as osync@cloud directly; a registration that does not lapse with a session's liveness (a durable cloud alias that keeps its inbox until explicitly removed); delivery to that alias readable from the linked thread. Keep the ownership rules (alias + host scope, [[feedback_alias_is_not_an_identity]]) and don't let one session take another live session's alias.

## Acceptance
- [ ] a linked cloud thread can register <alias>@cloud through the pgvector mailbox MCP (no file relay, no Remote Control card)
- [ ] the registration persists across the thread going idle; removed only explicitly or by an owner-set TTL
- [ ] send can carry from=<alias>@cloud for a durable alias this thread registered, and replies to it are listable/readable from the thread
- [ ] an alias held by a live local session can't be claimed; tests in tests/test_mailbox*.py; docs/mailbox.md updated
