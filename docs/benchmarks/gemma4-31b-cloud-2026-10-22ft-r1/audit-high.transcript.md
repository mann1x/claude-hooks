## Researcher (round 1)

The failure path for an unhandled exception in a parallel researcher lane is as follows:

### 1. Exception Capture in `researcher_node`
The `agent_loop.runner.run_loop` does **not** catch internal exceptions (e.g., HTTP timeouts or type errors in `tool_executor`); it allows them to propagate to the caller (`claude_hooks/agent_loop/runner.py:138-311`).
The `researcher_node` explicitly catches these exceptions in a `try...except` block (`consultants/engine/council.py:547-555`). Instead of crashing the graph, it returns a **tombstone state update** (`consultants/engine/council.py:563-573`) containing:
- `error`: `"researcher failed: <exception>"`
- `_role_failed`: `"researcher"`
- `research`: A list containing a failure string `"(researcher lane failed: <exception>)"`.
- `turns`: A `RoleTurn` marking the failure.

### 2. CouncilState's Additive Reducers
Because the researcher is fanned out via LangGraph's `Send` API, the results from multiple lanes are merged into the global state.
- The `research` channel in `CouncilState` uses `operator.add` (`consultants/engine/graph.py:64`).
- The tombstone `[err_text]` is concatenated with the reports from surviving lanes.
- Other additive fields (`turns`, `total_prompt_tokens`, etc.) are similarly merged (`consultants/engine/graph.py:68-72`).

### 3. Synthesizer's Input
The synthesizer consumes the merged `research` list (`consultants/engine/council.py:719`). It sees the surviving reports and the explicit failure string `(researcher lane failed: ...)` as part of the evidence.
The synthesizer does **not** fail; it simply synthesizes an answer based on the available (degraded) data.

### 4. Storage and User Perception
- **Status**: The `consultants/server/runner.py` checks `final_state.get("error")` (`consultants/server/runner.py:172`). Since `researcher_node` set the `error` key, `terminal_status` becomes `"failed"` (`consultants/server/runner.py:174`).
- **User Perception**: The user receives a **degraded but coherent answer**. The `final_answer` is generated by the synthesizer, but the metadata/status marks the consultation as `failed`.
- **Artifacts**: `storage.write_consultation` is called with `status="failed"` and the specific researcher error in the `error` field (`consultants/server/runner.py:177-199`).

**Conclusion**: The council produces a degraded answer rather than a total crash. The failure mode is a "Confidently Degraded" answer where the model ignores the gap left by the failed lane, though the metadata correctly flags the failure.

### Recommended Hardening
The synthesizer currently has no way to know *which* part of the plan failed, only that *some* research failed.

**Change**: In `consultants/engine/council.py:562`, include the `plan_item` in the `err_text` so the synthesizer can explicitly report which investigation step failed.
